# 雷达点云与 IMU 高低频数据异步处理架构说明

## 1. 背景
在 V11 多模态数据采集系统中，M300 激光雷达硬件通过**同一个 UDP 端口（6543）**混合发送两种截然不同的数据流：
- **IMU 报文（角速度与加速度）**：频率极高，通常为 **100Hz ~ 200Hz**。
- **点云报文（3D 坐标包）**：数据量极大，整体帧率较低，约为 **10Hz**。

如果在同一个监听线程中处理不当，极其容易引发系统级灾难：要么高频 IMU 丢失导致角度解算漂移，要么处理低频海量点云时卡死 CPU 导致线程崩溃。

## 2. 核心问题与破局方案

### 🔴 问题一：雷达倾斜安装导致的重力投影误差
**问题描述**：雷达安装在挖掘机顶部，物理上无法做到 100% 绝对水平。如果直接对 Z 轴角速度（`gyro_z`）进行积分来计算回转偏航角（Yaw），倾斜会导致实际旋转的物理面与雷达 Z 轴不共面，产生严重的“转一圈不够 360 度”的累计漂移。
**解决方法**：
设计了**开机静止联合校准与重力投影积分算法**。
1. 在程序启动的前 3 秒，提取三轴加速度计的均值，归一化得到雷达坐标系下的“绝对重力向上向量 (`up_vector`)”。
2. 运动时，将瞬时的 3D 角速度向量与 `up_vector` 进行**点积（Dot Product）运算**。无论雷达如何倾斜，点积都能精确提取出真实垂直于地面的旋转角速度，从而实现免疫物理倾斜的绝对精确积分。

### 🔴 问题二：高低频数据流在单线程内的阻塞冲突
**问题描述**：点云的坐标系矩阵转换和发布耗时较长（数毫秒级）。如果在 UDP 监听线程中每收到一个点云包就立即处理，会导致线程阻塞，从而漏掉在这个空隙间到达的 IMU 报文。
**解决方法**：
采用了**“IMU 实时预积分 + 点云时间节流批处理”**的高性能架构：
1. **共用极速网络 IO**：死循环全速调用 `recvfrom`，不让任何一个 UDP 包漏网。
2. **包头分流（Demultiplexing）**：根据首字节瞬间判定报文类型。
3. **IMU 实时处理**：如果是 IMU 包，利用极少的算力（微秒级）立刻进行梯形积分，更新底层偏航角状态，**绝不丢弃任何中间帧**。
4. **点云节流（Throttle Batching）**：如果是点云包，仅用 Numpy 极速提取 XYZ 并扔进内存缓存池 `pc_buffer`。设置一个 `0.1s` 的时间节流阀，只有当时间累积达到 0.1 秒（10Hz周期）时，才将缓冲池中的上万个点打包成一个数组送去转换和发布。

### 🔴 问题三：高频内部状态与低频 GUI/ROS 发布的矛盾
**问题描述**：虽然底层 IMU 积分达到了 200Hz，但如果以同样的频率去刷新 Tkinter UI 或发布 ROS `JointState` 话题，会导致界面无响应和网络带宽瞬间被撑爆。
**解决方法**：
**高频内部状态更新，低频消费者读取**。
底层的积分器 `DirectSwingAngleEstimator` 默默维护着高频累加的精准变量 `current_swing_rad`。而上层的 GUI 主循环（`_update_loop`）仅仅通过 `after(50, ...)` 机制，以稳如磐石的 **20Hz（每 50 毫秒）** 频率去“偷瞄”一眼这个累加好的数值，并进行发布。这完美符合了自动驾驶与机器人领域处理 IMU 数据的标准最佳实践。
