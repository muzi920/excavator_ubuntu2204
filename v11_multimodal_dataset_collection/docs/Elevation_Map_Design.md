# V11 雷达点云高程图 (Elevation Map) 算法设计与实现说明

## 1. 核心概念与背景
在挖掘机端到端强化学习任务中，将 3D 点云转换为 2D 俯视高程图（Elevation Map）是提取地形特征的关键手段。我们参考了网易伏羲开源的 `excavator-motion` 数据集规范，在 V11 系统中实现了实时的高程图生成与 ROS 2 发布功能。

## 2. 算法实现细节
### 2.1 物理映射范围
针对小型挖掘机工况，我们截取了以底座为中心的局部区域：
- **X, Y 轴范围**：$\pm 2.0$ 米（共 $4 \times 4$ 米的视野）。
- **分辨率**：$0.02$ 米/像素（2厘米精度），生成 $200 \times 200$ 像素的网格。
- **Z 轴高度压缩**：考虑到小挖机的物理局限，将关注的绝对高度区间设定为 `[-0.4m, 0.7m]`。低于地平线 40cm 的深坑映射为最暗（0），高于地面 70cm 的土堆映射为最亮（255）。

### 2.2 坐标系对齐 (与网易伏羲格式兼容)
为了直接复用开源算法，我们对图像的坐标映射进行了强制对齐：
- **底座居中**：挖掘机的底座中心永远位于图像绝对中心 `(100, 100)` 像素点。
- **正前方朝上**：将物理 X 轴正方向映射到图像的垂直朝上方向（v 轴取反），物理 Y 轴映射到水平方向（u 轴）。

### 2.3 伪多通道格式
虽然高程数据本质上是单一维度的，但为了对齐深度学习网络标准输入维度 `[200, 200, 3]`，我们利用 `cv2.cvtColor` 将单通道的 `0-255` 灰度物理映射严格复制为 BGR 三通道纯灰度图像。

## 3. 开发过程中的问题与解决方案

### 🔴 问题一：点云图像没有颜色，无法直观反映高度
**问题描述**：在早期版本中，ROS `/lidar/points` 话题只发布了 `x, y, z` 坐标，导致在 RViz2 中只能渲染成纯白色的无序点云，缺乏立体感和地形起伏的直观视觉反馈。
**解决方法**：
重写了 `sensor_msgs/PointCloud2` 的 `fields` 结构，追加了一个 `UINT32` 类型的 `rgb` 字段。在 Python 端实时计算每个点的 Z 轴灰度值（同样依据 `[-0.4, 0.7]` 范围），通过位移操作 `(gray << 16) | (gray << 8) | gray` 打包成伪彩色二进制数据，伴随坐标一同发布。RViz 开启 `RGB8` 转换后即可呈现立体的灰度起伏效果。

### 🔴 问题二：先验特征（铲尖位置）缺失
**问题描述**：高程图仅展示了地形，但在端到端学习中，网络需要知道当前铲尖的确切位置才能进行有效的闭环动作决策。
**解决方法**：
在高程图生成线程中引入了实时**正向运动学解算（Forward Kinematics）**。每一帧根据大臂、小臂、铲斗的角度，解算出铲尖在车体 `base_link` 下的 3D 绝对坐标，将其转换为高程图的 `(u, v)` 像素坐标，并在图像上绘制带有白色描边的红色醒目圆点。实现了地形与机器末端执行器位置的融合感知。

### 🔴 问题三：高频点云解析阻塞网络监听
**问题描述**：如果在 UDP 监听线程中每收到一个点云包就立即进行高程图投影和图像计算，会导致线程被严重阻塞，进而丢失同端口下高频传输的雷达 IMU 报文。
**解决方法**：
引入了 `queue.Queue` 异步解耦机制。UDP 线程仅做极简的点云 Numpy 提取并放入缓存；专门开启了第 7 个线程 `_elevation_map_loop` 作为消费者，在后台默默进行矩阵降维和绘图操作。最后以标准 `sensor_msgs/Image` 类型发布到 `/lidar/elevation_map` 话题。
