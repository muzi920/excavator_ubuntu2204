# 基于 v14_urdf 的统一控制接口规划

这份文档只做一件事：明确后续“统一控制接口”时，为什么要以 `v14_urdf` 作为统一基准，
以及统一后的接口应该长什么样、如何迁移、哪些内容先不动。

这不是实现文件，也不是代码改造说明。当前阶段只输出规划，不修改任何 `.py` 文件。

## 1. 规划目标

当前项目跨越了 `v1` 到 `v14` 多个版本，控制接口、传感器接入方式、ROS 话题和几何模
型长期并存。后续如果继续叠加功能，而不先统一接口，会越来越难维护。

因此这里把统一目标明确为：

1. 以 `v14_urdf` 的关节模型和 `URDF + /joint_states` 接口作为统一控制基准。
2. 让旧版本控制语义最终都映射到这套统一接口，而不是继续各自维护一套控制入口。
3. 让传感器接入逐步下沉为 C++ 节点，但不影响上层控制接口和规划接口。
4. 让实机控制、仿真控制、轨迹规划都围绕同一套关节语义组织。

## 2. 为什么选择 v14_urdf 作为统一基准

如果只从“哪个版本最早”来选，应该选 `v4`。但如果从“后续统一、可扩展、能兼容实机
和仿真”来选，`v14_urdf` 更适合作为基准层。

主要原因如下：

### 2.1 `v14_urdf` 已经把关节对象定义清楚

`v14_urdf` 当前已经明确使用标准关节名：

- `swing_joint`
- `boom_joint`
- `arm_joint`
- `bucket_joint`

同时它也保留了工程语义层的四个控制量：

- `swing_yaw`
- `boom_swing`
- `arm_boom`
- `bucket_arm`

这意味着它天然适合做“两层接口”：

1. 上层工程语义接口
2. 下层 URDF / ROS 标准接口

### 2.2 `v14_urdf` 同时覆盖了仿真与规划

`v14` 不只是 URDF 展示，它已经具备：

- `replay_json_script.py`
- `point_to_dig_dump_trajectory.py`
- `mode1_task_planner.py`

也就是说，`v14` 天然位于：

```text
控制语义 <-> 仿真执行 <-> 几何规划
```

这正适合作为统一接口的中心层。

### 2.3 `v14_urdf` 与 `v10`、`v4` 已经有天然连接

当前系统里：

- `v10` 提供几何 FK/IK
- `v4` 提供实机关节控制语义
- `v14` 负责把这两者带入 ROS / URDF 仿真

因此选择 `v14` 作为统一控制接口，不会破坏原有逻辑，反而能把：

- `v4` 的控制语义
- `v10` 的几何求解
- `v13` 的 ROS 标准化接口

统一到同一层。

## 3. 统一后的接口分层

后续建议把整个系统控制接口拆成三层，而不是再让每个版本混着定义。

### 3.1 语义控制层

这一层只关心“你要机械臂做什么”，不关心底层是实机还是仿真。

统一关节语义：

```text
swing_yaw
boom_swing
arm_boom
bucket_arm
```

统一控制目标：

```text
joint_name
target_value_deg
control_mode
tolerance_deg
speed_deg_s
aux_output
```

语义控制层的典型调用对象包括：

- 单点轨迹规划器
- 多点任务规划器
- JSON 剧本回放器
- 后续 `mode2` 轨迹生成器

### 3.2 ROS / URDF 执行层

这一层负责把语义控制量映射成标准 ROS 2 接口。

核心统一接口：

- 话题：`/joint_states`
- 消息：`sensor_msgs/msg/JointState`
- 单位：弧度 `rad`

统一映射关系：

```text
swing_yaw  -> swing_joint
boom_swing -> boom_joint
arm_boom   -> arm_joint
bucket_arm -> bucket_joint
```

也就是说，后续所有控制入口最终都要落到：

```text
JointState(name[], position[])
```

### 3.3 硬件执行层

这一层负责把语义控制量变成真实硬件动作。它可以继续存在，但不应该再作为“统一接口”
暴露给上层。

这一层未来可以有两种后端：

1. **仿真后端**
   - 通过 `/joint_states` 驱动 URDF
2. **实机后端**
   - 通过 CAN / 串口 / 液压输出驱动真实挖掘机

也就是说，统一接口是上层不变、后端可切换：

```text
同一套控制语义
-> 仿真执行
-> 或 实机执行
```

## 4. 统一后的最小控制接口草案

后续建议定义一个统一控制命令模型。即使暂时不写成消息类型，也建议所有版本按这个结
构理解控制请求。

### 4.1 单关节目标接口

```text
ControlTarget:
  joint_name: str
  target_value_deg: float
  tolerance_deg: float
  control_mode: str
  speed_deg_s: float
  ramp_up_s: float
  ramp_down_s: float
  aux_output_mv: int
```

其中：

- `joint_name` 只能取：
  - `swing_yaw`
  - `boom_swing`
  - `arm_boom`
  - `bucket_arm`
- `control_mode` 建议只保留：
  - `position`
  - `feedback_position`
  - `script_step`

### 4.2 多步骤脚本接口

后续统一脚本建议继续保留 `v14` 当前的结构，即：

```text
metadata
script[]
```

其中每个 `script` 元素至少包含：

```text
step
joint
description
target_val
ramp_up_s
ramp_down_s
aux_output_mv
```

也就是说，`v14` 当前的 JSON 结构本身就可以继续作为统一脚本接口的基础。

### 4.3 状态反馈接口

后续统一状态接口建议也按语义层组织，而不是直接暴露底层原始设备字段。

建议统一状态结构：

```text
ControlState:
  joint_name: str
  current_value_deg: float
  target_value_deg: float
  error_deg: float
  is_reached: bool
  status: str
  source: str
```

这样无论来源是：

- 倾角传感器
- 雷达 IMU
- URDF JointState
- 关节融合节点

上层都只读统一状态。

## 5. 旧版本到 v14 接口的映射规划

这部分只做规划，不做代码修改。

### 5.1 v1/v2 的映射

`v1/v2` 的控制本质是：

- 直接动作语义
- 时间开环
- 模拟量驱动

后续不建议继续作为统一接口暴露。它们应该下沉成“实机后端能力”，由统一控制层调用。

规划上可以理解为：

```text
v1/v2 = hardware backend
```

### 5.2 v4 的映射

`v4` 是最重要的语义来源。后续规划是：

- 保留 `boom_swing / arm_boom / bucket_arm / swing_yaw`
- 保留角度闭环思想
- 不再把 `v4` 视作最终接口层
- 让 `v4` 退到“实机执行后端 + 闭环控制策略来源”

规划上：

```text
v4 = semantic source + real-machine backend
```

### 5.3 v10 的映射

`v10` 不属于控制接口层，它属于几何求解层。

后续规划是：

- 继续保留 `FK / IK`
- 让其只服务于：
  - 单点轨迹生成
  - 多点轨迹生成
  - 工作空间分析

规划上：

```text
v10 = geometry engine
```

### 5.4 v12/v13 的映射

`v12` 和 `v13` 是后续传感器与标准 ROS 接口最值得继承的版本。

规划上：

- `v12` 重点继承 C++ 传感器节点架构
- `v13` 重点继承标准化 ROS Topic 命名与消息风格

也就是说，它们未来主要服务于：

```text
sensor backend
state publishing
hardware IO standardization
```

### 5.5 v14 的定位

`v14` 后续建议正式提升为：

```text
统一控制接口基准层
```

具体承担：

1. 统一关节语义
2. 统一 JSON 脚本结构
3. 统一 ROS / URDF 执行入口
4. 统一规划到执行的接口形式

## 6. 传感器 C++ 化后的边界规划

你已经明确后续“传感器接口会改成 C++ 版本”，这里提前把边界写清楚。

### 6.1 哪些内容建议改成 C++

优先建议迁移到 C++ 的内容：

1. 倾角传感器串口读取
2. 雷达 UDP 点云接收
3. 雷达 IMU 解包
4. 点云预处理与坐标变换
5. 相机 RTSP / USB 读取

这些内容适合 C++ 的原因很明确：

- 高频
- 长时间运行
- 对时延敏感
- 对阻塞敏感

### 6.2 哪些内容建议继续保留 Python

不建议急着迁移到 C++ 的内容：

1. 轨迹规划
2. 模式化任务生成
3. 点云 ROI / 匹配实验
4. URDF / RViz 辅助脚本
5. 离线分析与可视化

这些内容更偏算法试验和策略迭代，Python 改起来更灵活。

### 6.3 统一后的职责边界

后续建议系统职责边界写成：

```text
C++:
  传感器接入
  原始数据解析
  状态发布
  高频控制执行

Python:
  轨迹规划
  模式任务生成
  仿真验证
  离线分析
```

这能最大程度避免以后再次出现“既要高频接硬件，又要在同一个 Python 脚本里做 GUI、
点云处理和任务规划”的耦合问题。

## 7. 分阶段迁移规划

当前不要一次性大改。建议按阶段推进。

### 阶段 1：统一文档和命名

这一阶段只做规范，不动实现。

目标：

1. 明确统一关节语义
2. 明确统一 JSON 脚本字段
3. 明确统一 ROS Topic 命名
4. 明确 `v14` 是控制接口基准层

当前这份文档就属于阶段 1 的产物。

### 阶段 2：统一状态接口

这一阶段先统一“看见的数据”，再统一“下发的命令”。

目标：

1. 倾角、雷达 IMU、融合关节状态统一发布
2. 上层只读取统一状态，不再直接碰底层设备字段

### 阶段 3：统一控制命令接口

这一阶段把旧控制入口逐步收敛到一套统一控制命令。

目标：

1. 仿真后端使用 `v14 /joint_states`
2. 实机后端使用闭环控制执行节点
3. 上层轨迹规划不再区分实机与仿真

### 阶段 4：传感器接口 C++ 化

这一阶段再做底层替换。

目标：

1. 串口、雷达、相机下沉为 C++ 节点
2. Python 不再直接读硬件
3. 上层保持统一接口不变

## 8. 当前阶段不要做什么

为了避免接口统一变成“边改边乱”，这里明确当前阶段先不要做的事。

1. 不要一开始就同时改控制接口和轨迹规划逻辑。
2. 不要先动 `v14` 的规划脚本。
3. 不要先重写所有旧版本。
4. 不要先做大范围 `.py` 改造。

当前最重要的是先把“统一接口长什么样”写清楚。

## 9. 推荐的统一入口目标

如果以后完成统一，建议你把系统的主要入口收敛成四类：

1. **传感器启动入口**
   - 启动所有 C++ 传感器节点
2. **控制执行入口**
   - 接收统一控制命令并执行
3. **仿真验证入口**
   - 启动 `v14_urdf` 和 `/joint_states`
4. **规划任务入口**
   - 单点 / 多点 / `mode1` / `mode2`

也就是说，未来不再以“版本目录”作为入口，而是以“功能入口”作为入口。

## 10. 当前规划结论

如果只用一句话概括当前规划，可以写成：

> 后续统一控制接口时，以 `v14_urdf` 的关节模型、`/joint_states` 执行形式和规划 JSON
> 结构作为统一基准；以 `v4` 保留控制语义与实机闭环逻辑；以 `v12/v13` 作为传感器 C++
> 化与 ROS 标准化的主要继承来源。

这也是当前最稳、最符合你现有代码资产的统一路线。
